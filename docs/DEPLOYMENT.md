# 部署与维护

## 当前交付

独立重构项目与原 GitHub Pages 站点分离。安全预览仅对拥有者开放，网站内部仍要求现有 Supabase 账号登录。源代码及静态构建均不含私人图片、正文、草稿、密码或 Service Role Key。

## GitHub Pages

1. 最终验收前，使用独立测试仓库或独立部署地址；不要直接替换唯一可运行旧站。
2. 对源码运行 `npm ci`、`npm test`、`npm run build`。
3. 将 `dist/` 内容发布到目标 GitHub Pages。`.nojekyll` 由构建生成。
4. 所有资源采用相对路径；Hash 路由支持 `/仓库名/#/library` 等子路径和直接刷新，不需要服务器重写规则。
5. 验证真实账号登录、刷新、私人素材、作品及创作保存后，再由用户明确批准正式站点切换。

如果选择 GitHub Actions，应使用手动触发的独立预览工作流，并把 Pages 权限与目标环境配置为测试地址。此交付不会自动触发原仓库的生产部署。

## Supabase

继续使用原项目和已有账号。Publishable Key 可以出现在前端；权限由 Auth、RLS 及 Storage 策略执行。不要添加 Service Role Key，不要公开素材 Bucket，也不要把正文或草稿写入静态构建。

用户批准的迁移已经应用。如果将来另建后端，应先完整迁移现有 schema、函数、授权和 RLS，再审查补充迁移；不要只运行这一个文件期望建立整个后端。

## 添加作品和邀请好友

管理员从首页或创作管理新增作品；建立卷、章、小节后保存草稿，使用预览检查，最后明确发布。封面上传到私人 `story-art/covers/<work-id>/<random-name>`，复用 `works.cover_url` 存路径。

邀请好友先在 Supabase Authentication 中创建账号，再在管理员设置中关联 UID 为 reader 档案，授权指定作品。网站无公开注册入口，Auth 也已确认关闭公开注册。

## 日常维护

业务查询集中在 `src/services/data.js`，页眉和导航集中在 `src/components/shell.js`。首页构图不要通过新背景或重复 CSS 覆盖修改；涉及美术变更先与确认截图对照。新增页面复用 Shell，只实现业务内容，并提供卸载清理函数。

升级依赖时更新锁文件并重跑单元和浏览器测试。数据库权限变更必须先提供独立 SQL，检查兼容性，并取得明确批准。生产小说与账号不能作为测试夹具。

发布过程当前是现有小节 RPC 加父级状态更新的分步流程。若未来需要整个作品一次原子发布，可单独审查事务 RPC 迁移；本次没有擅自改写原发布函数。多作者协作和跨设备同时编辑若变得常见，再引入乐观锁，避免无必要地改变当前 schema。
